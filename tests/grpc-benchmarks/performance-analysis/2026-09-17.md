# Attainable performance of the kotlinx-rpc Swift gRPC backend

## 1. Executive summary

**The direct Swift client is a credible near-parity target for some workloads, but the data does not support a universal parity percentage.** Current retains 86–90% of Swift throughput in the longer sequential small-unary cases, 88–91% in ping-pong, 92–94% in large-response streaming, and approximately 100% in 1 KiB upload streaming. It reaches 110–123% in three full-duplex cases. Conversely, small-response streaming retains only 60–65%; high-concurrency 1 KiB unary falls to 35–37%; large upload unary retains 18–20%. These are **Measured**, single-run comparisons, not confidence intervals. All 52 cases and four primary latency metrics are tabulated below and in the reproducible data appendix. (Q)

**Observed**, avoidable current-side work includes a Swift task for every response event, an extra rendezvous channel between grpc-swift and Kotlin, a Kotlin request collector plus a coroutine for every request pull including EOF, repeated normal-path cancellation/error construction, common event wrappers, eager metadata conversions, and protobuf marshalling through an additional native C++ wire bridge. Each response is copied into a Kotlin buffer before decoding; each request is encoded into a Kotlin buffer before copying into NIO storage. Direct Swift avoids those intermediate Kotlin buffers, but still encodes/decodes protobuf, creates request-processing tasks, crosses into the NIO event loop, frames messages, and copies payload fields. (K1–K8, B1–B4, P1–P4, D1–D9)

**A material lifetime concern deserves investigation before performance tuning:** the native encoder holds a stable reference to an inner context which references the encoder that owns its cleaners. The only disposal shown is cleaner-driven. This is the indirect retention pattern the Kotlin cleaner contract warns about. It is also present in the published legacy revision, so it is not a Swift-backend regression, but fixing it may still close the current/Swift gap. The source supports a serious retention hypothesis; it does **not** establish that GC or a leak caused any particular CSV pause. Decoder cleanup also warrants review before pooling: its explicit close destroys a C++ member that later `delete` would ordinarily destroy again. (P2–P5, D14; O1)

The highest-value sequence is:

1. Establish binary/build provenance and reproduce tails; current HEAD already adds explicit imported-Swift Release configuration.
2. Audit native encoder/decoder resource lifetime; make request-source cleanup once-only and construct errors only for a waiting consumer.
3. Replace task-per-event response pulls with a bounded callback mailbox; specialize single-request and single-response paths while retaining interceptor ordering.
4. Reduce request-pull coroutine churn, then optimize serialization and safe buffer filling/decoding.
5. Tune flush/batching and NIO only with both Swift clients as controls. Shared improvements must not be presented as bridge-gap removal.

**Attainable parity:** roughly 90–98% retention is a reasonable *conditional engineering target* for sequential small calls and large-response streaming; 80–95% is a useful target band for small-response streaming after removing event handoffs. High-concurrency unary and request-heavy bulk workloads can plausibly narrow their gaps substantially, but their numerical ceilings remain poorly identified until lifetime, build flags, and long pauses are measured. Section 7 gives explicit scenario assumptions, including cases where a numerical forecast would be unjustified. Exact throughput parity is architecturally possible when common transport/server work dominates or overlaps Kotlin work; exact equal CPU cost is not expected. No positive universal “unavoidable penalty” can be derived from these measurements.

No production code was changed, no commits or remote changes were made, and no Apple binaries or benchmarks were built or run.

### Input identity and evidence vocabulary

Input is the CSV appended to this run's prompt: 156 rows, 52 paired benchmark/case keys, ten families. It has no run timestamp, machine identity, binary hash, compiler invocation, originating revision, raw per-operation timestamps, or repeat identifier. Treat it as **one run**. The analysis preserves all 156 throughput values and current/Swift mean, p50, p95, p99 for every case; selected historical mean/p50/p99/p999/max values are also preserved. This is a selected-field transcription, **not** a byte-for-byte copy or hash of the original CSV. Input hashes and the script document exactly what was preserved. (Q)

- **Measured:** calculated from supplied CSV only.
- **Observed:** established by inspected source/history; not proof a benchmark binary used it.
- **Strong inference:** supported by converging source and measurements, with alternatives stated.
- **Hypothesis:** requires a controlled experiment.
- **Unknown:** evidence cannot distinguish alternatives.

Linux cannot execute the Apple implementations. No scheduling counts, GC durations, byte-copy totals, CPU profiles, thermal measurements, or validated speedups were obtained. Static task and callback counts below describe source invocations, not guaranteed suspensions or physical thread switches. No additive decomposition of C/S into runtime, bridge, serializer, and transport costs is claimed.

### Interpretation of every family

**Small unary:** standalone empty mean is 432.015 versus 289.419 µs, retention 67.0%, but empty-c1 is 404.479 versus 363.237 µs, retention 89.8%. Different call counts and run positions prevent treating these as interchangeable repeat trials. Small-payload sweeps are more consistent: about 47–57 µs excess mean and 87–89% throughput retention. The additional setup/handoffs are real source work; attributing a universal 143 µs to the bridge is unsupported. (Q, K1–K7, B1–B3)

**Unary concurrency:** empty throughput peaks around current c32 at 11,061/s, while Swift reaches 21,677/s at c128. At 1 KiB, current reaches only 8,694/s; Swift reaches 24,082/s at c64. At c128 current/Swift p50 latency is 6.209/5.274 ms (84.9% retention), but mean is 14.717/5.400 ms (36.7%), p99 is 359.773/7.775 ms (2.2%). The standalone c16 throughput run has current p999 403.374 ms versus Swift 2.023 ms. **Strong inference:** long stalls materially distort mean throughput and scaling. **Unknown:** GC, stable-root growth, cleanup, executor starvation, server interference or build configuration contribution. Overlapping stalled calls cannot be summed as independent wall-time losses. Note disconfirmation of uniform tail inferiority: current 1k-c16 p95 and p99 beat Swift, even though its mean is twice as large. (Q)

**Payload sweeps:** upload-64k is faster than upload-1k in Swift (224 vs 384 µs mean), despite more bytes; current median also falls from 420 to 330 µs. This is consistent with the shared 64 KiB flush threshold, not a linear copy-only model. At 1 MiB and near-4 MiB upload, medians retain only 40–41%, so removing outliers alone will not reach parity. Downloads are different: median retention is 91.5% at 1 MiB and 96.9% near 4 MiB despite mean retention 56.7% and 39.5%. Symmetric near-4 MiB median retention is 97.6% versus mean 39.0%. Those mean gaps cannot honestly be labeled an inherent per-byte cost. (Q, D5)

One current upload-1m maximum of 393.356 ms is 55.5% of its 708.935 ms sequential elapsed time. A single maximum is not a fitted tail model, but demonstrates why median-only and mean-only conclusions are both incomplete. With only 50 near-4m unary observations or 17 fixed-byte stream writes, p99/p999 can select the same individual maximum; no distributional tail guarantee follows. (Q; supplied elapsed/max fields)

**Client streaming:** retention is 100.9%, 67.8%, 53.6% for 1k/64k/1m. At 1k current p50 write is 8.333 µs versus Swift 0.916 µs, yet total goodput matches. Swift buffers/flushes differently; cheap write acceptance does not mean faster server delivery. Current p99 write at 1k is 708.958 µs versus 29.958 µs, while Swift p999 is 3,803.542 µs versus current 856.625 µs: stalls occupy different quantile regions. Final response latency C/S is 1,512.667/1,480.500 µs at 1k, 579.208/450.542 at 64k and 1,439.792/2,619.542 at 1m. No universal teardown multiplier fits. (Q, H3–H4, D4)

**Server streaming and stream concurrency:** 1k response goodput retains 64.8%; c1–c16 retain 60.3–63.1%. Current saturates near 63k messages/s and Swift near 100k. Equivalent service time from aggregate throughput differs by about 5.5 µs/message in the 1k server test (1/C−1/S); this is a saturation budget, not an isolated bridge benchmark. Current median inter-arrival is ~10 µs versus Swift ~1.7–1.8 µs, with sometimes *better* current p95. A task/channel per event prevents draining available bursts as cheaply as direct iteration, while altering burstiness. Large-response streaming retains 91.9–93.5%, supporting amortization of a fixed event cost; 1m p99 is still 8.379 ms versus 2.860 ms. Extra streams do not cure the small-response ceiling. (Q, B1–B2, D4)

**Ping-pong:** current means exceed Swift by 28.834 µs empty and 42.086 µs at 1k. Call setup is amortized across 10,000 exchanges, so a purely per-call explanation fails. Both clients are far behind legacy in ping-pong (~44–51% of legacy throughput), supporting a shared low-load Swift transport/concurrency candidate. Removing shared flush delay can improve absolute latency while making the remaining relative bridge tax *more visible*. (Q, D5)

**Full duplex:** balanced1k retention 92.1%, balanced64k 122.5%, upload-heavy 115.8%, download-heavy 110.0%. (Q, H3–H4, D4–D7)

Balanced1k first response is 101.176 ms current versus 21.314 ms Swift. Subtracting only those intervals from outer elapsed leaves approximately 211.166 vs 266.259 ms; those are **diagnostic residual intervals**, not valid steady-state throughputs, because startup overlaps request production. Download-heavy first response is also long in both clients (22.234 vs 28.181 ms). Include startup and burst profiles when reconciling throughput wins with latency differences. (Supplied elapsed/first-response fields)

**Fixed 64 MiB upload:** current 41.8/528.4/1189.1/799.8 MB/s versus Swift 41.8/875.5/2250.6/1941.1 MB/s at 1k/64k/1m/near4m. Retentions 100.0/60.4/52.8/41.2%. Current p50 write retention is already 92.3% for near4m; p99 retention is 12.6%. (Q, H3–H4)

**Legacy context:** current is faster in all client-streaming, fixed-byte upload, full-duplex and small stream-concurrency rows; it loses most unary and ping-pong rows. Swift becomes faster than legacy at higher unary concurrency, yet large-response Swift streaming is itself slower than legacy. These facts localize questions but are not a causal decomposition. The same Kotlin protobuf lifetime concern exists in legacy, whereas the Swift baseline omits it. (Q, G3, P2)

## 4. Architecture and call-path comparison

### Common current entry path

Generated service call → `unaryRpc` / streaming counterpart → `rpcImpl` cold Flow → fresh `ClientCallScopeImpl` and interceptor chain → `GrpcClientTransport.execute` → iOS `SwiftGrpcClientTransport` → `SwiftManagedChannel.startCall`. Common `GrpcClientCallEvents` are collected and mapped to response Flow emissions and headers/close callbacks. These nested Flow layers allocate/wrap and invoke suspend functions; **they do not inherently create a dispatcher hop**. Headers and trailers must still reach interceptors, and retries must recollect a new call scope. (K1–K2, K7)

### Request direction: current versus Swift

**Current:** request Flow → eager undispatched Kotlin collector → rendezvous `Channel<Request>` → Swift request producer calls `nextRequestMessage` → Swift checked continuation/cancellation handler → Objective-C `nextRequestWithCompletion` → Kotlin atomic pending slot and undispatched child coroutine → channel receive → generated Kotlin marshaller → native `WireEncoderNative`/C++ wire routines → Kotlin Buffer → Kotlin NSObject request wrapper → completion resumes Swift → allocate zero-initialized `GRPCNIOTransportBytes` → `length` property crossings and `fillBuffer` callback → segment pin/memcpy → `writer.write` → identity RawMessage serializer → NIO async writer/event loop → gRPC framer → HTTP/2 → Network.framework. EOF is an additional request pull. (K3–K5, B2, B4, P1–P2, D1–D8)

**Swift baseline:** generated Swift service API → `ClientRequest` or `StreamingClientRequest` producer → `writer.write` → `ProtobufSerializer` → SwiftProtobuf size traversal, allocate zero-initialized transport bytes, encoding traversal directly into those bytes → same grpc-swift/NIO writer/framer/HTTP2/Network.framework path. No Kotlin Buffer or request-source callbacks, but not zero protobuf work or zero initialization. (H2/H4, D1, D8–D9)

### Response direction: current versus Swift

**Shared:** Network.framework supplies Data → NIOTS copies into ByteBuffer → HTTP/2 parsing/multiplexer → gRPC deframer, which slices a complete buffer or accumulates incomplete bytes → NIOAsyncChannel inbound queue (default low/high 2/10 elements) → grpc-swift body-parts iterator. (D3–D7)

**Current:** identity RawMessage deserializer → `SwiftGrpcMessageEvent` → `AsyncThrowingChannel.send` rendezvous → separate task created by Kotlin's `nextEvent` call → completion → Kotlin cancellable continuation resumes → scoped `withUnsafeBytes` → segment copies into Kotlin Buffer → native CodedInputStream reads pinned Buffer segments → response bytes field copied to an owned ByteArray/ByteString → `GrpcClientCallEvents.Message` → common event-to-response Flow → caller validation/collection. (B1–B4, K4–K6, P3–P4)

**Swift baseline:** generated SwiftProtobuf deserializer consumes contiguous transport bytes directly and copies a `bytes` field into Data → typed response consumer/validation. Direct iteration retains one logical iterator. Swift does not eliminate the message object's owned payload copy, but avoids current's entire encoded-input Buffer copy and Kotlin/C++ field calls. (D2, D9)

### Call-shape inventory

Let R=request messages, M=response messages, E=accepted headers + messages + terminal event. For ordinary successful finite RPCs, E=M+2. Early rejection/cancellation has a different count. “Task” and “coroutine” count below means explicit source creation, not distinct running OS threads.

| Shape | Current bridge additions over shared grpc-swift | Direct Swift API/path |
|---|---|---|
| Unary | One call Task + normally 3 event-pull Tasks; 3 fresh channel iterator values and Kotlin completion adapters; request collector + 2 request-pull child coroutines (one message, EOF); request and response buffer copies | Generated unary → core unary → streaming single-request wrapper → same core bidi executor; unary response adapter consumes cardinality/status internally |
| Client streaming | One call Task + normally 3 event-pull Tasks; collector + R+1 request-pull coroutines/Swift checked continuations; R serialized buffer transfers | Generated client-stream API; producer writes R messages directly; one response adapter |
| Server streaming | One call Task + M+2 event-pull Tasks if finite; collector + two request pulls; M copies and Flow event wrappers | Generated server-stream API with single producer and direct response iterator |
| Ping-pong | Long-lived bidi setup; each iteration uses request pull machinery plus response event task/continuation and Kotlin Channel(1) benchmark gate | Generated bidi; Swift AsyncStream token gate plus writer/response iterator |
| Full duplex | Same per-direction work as bidi; request collector and grpc-swift request task progress independently of receive event delivery | Producer and response consumer overlap within core task-group topology |
| Server benchmark take(N) | Usually headers+N message pulls, then cancellation rather than successful Closed; extra cancel-and-wait Task and Kotlin suspension | Return from scoped handler after N messages triggers group cancellation/stream close |

The direct unary response adapter performs three body-iterator reads (message, trailers, end-of-sequence). The current runner finishes on trailers and delivers Closed to Kotlin before its own deferred cleanup is necessarily finished. Thus even nominal RPC-completion timing and resource quiescence differ; simply copying the direct unary adapter may add a final drain while removing bridge trips. Count both, rather than assuming the baseline avoids all terminal work. (D1–D2,B2)

For a 10,000-response successful bidi, the current bridge introduces about 10,002 pull Tasks in addition to its call Task, not 10,000 new RPCs. A finite R=10,000 request stream invokes 10,001 pulls if exhausted normally. A one-million-message stream magnifies those invocation counts but not necessarily live memory: sequential demand bounds pending bridge work. Metadata entries add their own synchronous callbacks. Getter/fill callbacks make byte-boundary crossing counts greater than “one crossing per message.” Their exact compiled count/ARC cost requires generated bridge inspection/profiling. (K3–K6, B1–B4)

### What both clients pay below the bridge

Core unary, client-streaming and server-streaming APIs all delegate to `bidirectionalStreaming`; it takes a client-state mutex, merges method configuration, and selects execution policy. With default no retry/hedging and no deadline, `OneShotExecutor` creates a task group and `ClientStreamExecutor` adds a request-processing task. Response processing waits for initial metadata and transfers its iterator into the body sequence. A deadline adds timeout/execution tasks; those are not a justified culprit for these default cases. (D1–D2)

Transport channel/subchannel state is synchronized; opening a stream asynchronously initializes a GRPC handler and NIOAsyncChannel on its event loop. Writer delegates call `eventLoop.execute` when off-loop; batched writes can share that submission and flush. Receive delivery yields batches at read-complete; low-water resumption may hop back to the event loop. NIO writer acceptance is not a socket/server acknowledgement. Neither Swift nor Kotlin source permits counting every `await` as a hop. (D3–D4)

Default client HTTP/2 receive settings: max frame 16 KiB, target window 8 MiB. Window manager accounts for buffered frames and generally replenishes when remaining effective window is at most half target. These receive advertisements do not enlarge the server's receive window for uploads. Flush coalescing requests a 100 µs delay unless 64 KiB accumulates, writability changes or close forces progress; scheduled execution may be later under load. Both clients inherit it. (D5, D10)

Identity framing copies the serialized payload into a framing buffer; large framing buffers are discarded beyond the 64 KiB retention threshold. Deframing is not always copying: a complete message uses `readSlice`; fragmented data can require append/COW/compaction. NIOTS outbound `getData` copies at <=256 KiB per buffer, otherwise can retain ByteBuffer storage, but HTTP/2 fragmentation affects actual buffer size. NIOTS inbound explicitly copies Data into ByteBuffer. Actual copy multiplicities depend on frame fragmentation, ownership and batch shape. (D6–D7)

### Cancellation, completion, and historical contrast

Current Kotlin cancellation invokes Swift call cancellation and request-source cancellation. Swift request continuations require the callback to be completed; checked continuations do not cancel themselves. The Swift runner checks cancellation before and after AsyncThrowingChannel sends because send returns normally on cancellation. PullState allows one outstanding pull and becomes terminal before completion callbacks, enabling controlled reentrancy. Successful trailers are delivered before channel finish. Kotlin marks `closed` only after downstream emission; an interceptor exception therefore triggers cleanup. Early collection termination uses NonCancellable cancel-and-wait; normal close need not await every Swift cleanup step before the measured Kotlin call returns. Lifetime experiments must measure resource quiescence separately from user completion. (K3, K6, B1–B4)

Pre-split main performed listener/callback adaptation directly in the common call layer: unary/server-stream requests used `requests.single()` with one sender coroutine; client/bidi requests had an eager collector and rendezvous channel; responses used a capacity-one channel with readiness callbacks. Today's nonIos transport carries event objects through a callback/event channel; its `ManagedChannel.createCall` expect resolves in nonIosNative to `NativeManagedChannel.newCall`/`NativeClientCall`, C-core batches, readiness state and completion-queue callbacks. The moved NativeClientCall body is unchanged by source relocation. C-core still copies into/out of its representation; that does not make those costs irrelevant to a Swift-target investigation. The iOS path does not traverse today's nonIos callback channel. (G1/G3, K9–K11)

## 6. Complete optimization inventory

Categories: **G** closes current-versus-Swift gap; **S** shared absolute improvement, not necessarily relative parity; **B** changes workload/baseline and must be tested in both; **D** deferred until profiling. Effort: small, medium, large. Impact descriptions are hypotheses unless explicitly stated otherwise. Every candidate preserves cold-flow semantics, metadata callbacks, cardinality/status, cancellation, ordering and byte/message bounds; additional candidate-specific obligations follow.

### O1. Make native protobuf lifetime deterministic and break encoder retention (G)

**Location/current:** `WireEncoderNative.Ctx`, `context`, `contextCleaner`, `rawCleaner`, `flush`; generated `generateMarshallerObject`; `WireDecoderNative.close`; `pw_decoder_close/delete`. Native encoder owns a StableRef to its inner context, which can keep the owner/cleaners alive. Decode disposes its StableRef explicitly but deletes native storage later via a cleaner. **Baseline:** SwiftProtobuf uses scoped Swift values and no such Kotlin StableRef/C++ encoder lifecycle. (P1–P5, D14)

**Design:** first isolate allocation/deallocation counts; move encoder context into an owner-independent holder of the sink, then introduce scoped, exactly-once native release with a safe fallback cleaner state. Generated marshalling must release on success and encode/flush failure. Do not simply delete the raw pointer while a cleaner can later delete it again. Audit decoder close: explicit member destruction followed by automatic member destruction on delete is a C++ lifetime hazard even if a particular destructor happens to leave an empty backup region. A resettable/optional member or single destruction path is needed before pooling.

**Impact:** all request shapes; potentially high cumulative memory/tail benefit, unknown throughput gain. Present in legacy too; still G. **Confidence:** high graph observed, strong retention concern, unknown runtime manifestation. **Owner/effort/risk:** protobuf/kotlinx-rpc, medium, high lifetime correctness. **Experiment:** N isolated encodes at fixed payload, drop references, record native new/delete and StableRef create/dispose/live heap after quiescence; repeat with owner-independent/scoped variant; ASan/UBSan decoder close tests. Lack of live-count growth falsifies the strongest leak mechanism, but not cleaner overhead.

### O2. Make request-source cleanup once-only and lazily create NSError (G)

**Current/location:** `KotlinGrpcRequestSource.cancel` allocates CancellationException and `swiftGrpcError` before `complete` discovers there is no waiter. Calls arise from Kotlin finally, parent completion, Swift producer defer, CallRunner defer, explicit cancel and deinit. **Swift baseline:** core cancellation without this Kotlin error bridge. (K3, K6, B1–B4)

**Design:** synchronized terminal state wins once; first detach/cancel producer resources, atomically claim an outstanding completion, then construct error only if needed and invoke outside synchronization. Preserve original failure. Later pulls after terminal must promptly complete; guarding only cancel with a Boolean would otherwise risk orphaning a new waiter. Dispose parent-completion registrations at safe termination if retained longer than needed.

**Impact/cases:** small unary/concurrency most, every call; lower allocations, not proven pause cure. **Confidence:** high avoidable construction, medium impact. **Owner/effort/risk:** Kotlin bridge, small–medium, completion/cancellation races. **Experiment:** counters for cancel invocations, effective transitions, NSError created without waiter; empty-c128 and normal/early-terminal client streams. Force cancel-before-registration, reentrant completion, late pulls and encoding failure.

### O3. Replace per-event Swift Task and async-channel relay with a bounded callback mailbox (G)

**Current/location:** `SwiftGrpcCall.nextEvent`, `PullState`, `CallRunner.send` relay every event through AsyncThrowingChannel and a new Task. **Baseline:** directly iterates grpc-swift response body. (B1–B2,D2,D11)

**Design:** one call-running task owns response iteration. A synchronized mailbox matches a pending Kotlin callback to a produced event; only the producer suspends when no demand exists. Move callback invocation outside the lock after transitioning state; maintain one outstanding demand and bounded in-flight event. A callback may request another event synchronously, so avoid recursive delivery loops/unbounded stack growth with a drain guard. Unify terminal/failure/cancel state without discarding an accepted terminal event.

**Impact:** broad, especially server1k, stream concurrency and unary task pressure; removes E explicit pull Tasks, not E unavoidable network events. **Confidence:** high structural reduction, medium speedup. **Owner/effort/risk:** Swift bridge, medium, high concurrency/cancellation burden. **Experiment:** old/new server1k and c128; task creation and event-to-consumer delay counters; slow consumer, concurrent pulls, headers callback throwing, cancellation at every state. No throughput/CPU change deprioritizes further mailbox sophistication.

A conceptual mailbox transition (not compiled implementation) is:

```text
next(callback):
  under lock: reject concurrent/terminal pull; register demand
  if an event is ready: claim event + callback, update state
  outside lock: complete callback; release producer credit
produce(event):
  under lock: match demand, or retain one bounded event and suspend producer
  outside lock: invoke any claimed callback; never block the event loop
cancel/fail:
  under lock: enter terminal; detach waiter and producer continuation
  outside lock: wake both exactly once; release owned event storage
```

Cancellation must remain distinguishable from an orderly Closed event. The pseudocode omits implementation-specific synchronization and error storage; it is a design invariant sketch, not a ready patch.

### O4. Single-request bridge specialization (G)

**Current/location:** unary and server streaming use `flowOf`, `KotlinGrpcRequestSource`, collector/channel, message+EOF callbacks. **Baseline:** `StreamingClientRequest(single:)` supplies one materialized request directly. (K1,K3,B4,D1)

**Design:** optional single-request transport operation after interceptor processing; encode exactly one request and supply it directly to Swift. Keep generic Flow fallback for interceptors which transform requests or rely on subscription semantics. Alternatively use a tiny synchronous one-item request source, avoiding coroutine/channel creation while preserving the existing bridge contract.

**Impact:** small unary latency/high concurrency and server-stream startup; little long-stream goodput effect. **Confidence:** high redundant machinery; medium impact. **Owner/effort/risk:** common API + Kotlin/Swift bridge, medium; cardinality, replay and credential/interceptor ordering. **Experiment:** compare direct singleton vs callback singleton vs old path, count collectors/pulls/tasks and timestamps around headers. Recollection must start fresh calls; malformed multi-request unary must still fail correctly. Merely invoking grpc-swift `unary` is insufficient because its core still uses bidi.

### O5. Single-response/unary completion envelope (G)

**Current/location:** headers, one message and terminal status each require a separate event pull and Kotlin continuation. **Baseline:** `ClientResponse(stream:)` aggregates a single response internally and checks cardinality. (K4,B1–B2,D1)

**Design:** return one response/status envelope for unary and client streaming, eliminating message/terminal round trips where semantics permit. If headers observers exist, deliver their callback before body handling; do not defer observable headers until RPC completion. Preserve zero/multiple response errors and status/trailers even after a body was received. Retain generic mode for interceptor semantics that cannot be represented.

**Impact:** unary/concurrency and client-stream final response; generally more valuable per-call than large-stream throughput. **Confidence:** high count reduction, medium impact. **Owner/effort/risk:** common + Swift bridge, medium–large, API and interceptor compatibility. **Experiment:** no-interceptor unary fast path versus existing path; add delayed body after headers, close interceptor exceptions, non-OK after message, cancellation and deadline variants. Never report success before final status.

### O6. Eliminate per-request pull coroutine and redundant channel traversal (G)

**Current/location:** each `nextRequestWithCompletion` launches an undispatched coroutine to receive from a separate rendezvous collector. **Baseline:** producer loop directly writes messages in its existing core request task. (K3,B4,D2)

**Design:** persistent Kotlin collector meets a pending Swift request callback in a bounded handoff state machine. It suspends between demand credits and completes Swift with an encoded message. Keep eager subscription for streaming even if RPC fails before first pull. A smaller A/B uses `tryReceive` only as a safe fast path with a correctly synchronized suspend fallback; never spin waiting for demand.

**Impact:** ping-pong/request-heavy small messages; high-concurrency unary if O4 unavailable. 1k upload already at parity, so expect CPU savings before throughput. **Confidence:** high churn observed, medium effect. **Owner/effort/risk:** Kotlin bridge, medium, cancellation/race/reentrancy. **Experiment:** R+1 coroutine count should drop to O(1) per stream; slow producer, early server rejection, flow initialization failure, and sustained 1k/64k uploads. Reject any design with unbounded queued emissions or late callbacks after source disposal.

### O7. Persistent response iterator as an isolated micro-experiment (G,D)

**Current/location:** `nextEvent` creates a fresh `AsyncThrowingChannel.Iterator` per event. **Baseline:** retains its response iterator. However, exact AsyncAlgorithms iterator is a small value wrapping shared ChannelStorage, not a fresh queue or independent subscription. (B1,D11)

**Design:** if keeping task-per-pull temporarily, isolate a persistent iterator under a single owner; do not concurrently mutate a stored iterator across unstructured Tasks. Prefer O3 because it removes the channel/Tasks too.

**Impact:** minor reference traffic at most; no basis for assigning the server1k gap to iterator allocation alone. **Confidence:** high wrapper-only observation, low performance value. **Owner/effort/risk:** Swift bridge, small–medium, Sendable/isolation constraints. **Experiment:** allocations/ARC samples and same server1k run with only iterator lifetime changed. No improvement is expected to rule out larger O3 benefits. A shared unsynchronized iterator is rejected.

### O8. Batch bridge events with bounded byte credits (G)

**Current/location:** one callback/task/continuation per response; direct Swift can drain buffered arrivals cheaply. (B1–B2,K4,D4)

**Design:** demand returns up to N available messages with a byte cap, never waits to fill a batch in latency-sensitive mode; preserve headers-first and terminal-last, propagate status after all preceding messages. Batch owned event buffers, not borrowed pointers escaping their callback. Kotlin emits them sequentially and checks cancellation between items. A max batch budget is per stream and channel; do not rely on message count alone for MiB payloads.

**Impact:** small-message server/full-duplex throughput and crossing frequency; little ping-pong benefit. **Confidence:** medium; actual grpc-swift readiness API may require mailbox buffering rather than speculative `next` calls. **Owner/effort/risk:** Swift/Kotlin bridge, medium–large, slow-consumer memory and fairness. **Experiment:** N=1/4/16 plus byte cap; response1k and slow consumer, tail/CPU/RSS; immediate first-item delivery. Do not trade bounded memory for a misleading throughput win.

### O9. Bound and tune request prefetch/batching (G/B)

**Current/location:** rendezvous bounds request collection, then NIO has its own buffered writer; Swift loops may fill it more cheaply. (K3,B4,D4)

**Design:** test a tiny byte-bounded request queue or a pull-batch API; perform one bridge completion for several encoded messages and, where supported, one writer batch. Keep stream message boundaries and per-message cancellation checks. Prefetch may execute user Flow side effects ahead of actual demand, so compatibility must be explicit; default remains conservative. Record buffered bytes in every layer, not just Kotlin's queue.

**Impact:** request-heavy throughput, scheduling amortization, possibly full duplex. **Confidence:** medium mechanism, low likely gain at 1k already transport-limited. **Owner/effort/risk:** bridge, medium; cancellation latency, memory and changed producer backpressure. **Experiment:** 1/4/16 message and byte-credit variants with slow server/network and asymmetric rates. Compare Swift using equivalent batch writer separately (B), preserving the original baseline too.

### O10. Remove intermediate request Buffer with an optional encode-into-storage contract (G)

**Current/location:** generated marshaller builds Kotlin Buffer, then `KotlinGrpcRequestMessage.fillBuffer` copies segments into NIO storage. SwiftProtobuf already encodes into final contiguous transport bytes. (P1–P2,K5,B4,D8–D9)

**Design:** optional native marshaller specialization provides encoded length and synchronous `encodeInto(pointer,capacity)` into Swift-owned storage, with fallback to current Source marshallers. A size traversal or cached immutable size may be needed; account for its CPU cost. The encoder must not publish partially initialized bytes, retain pointers, or run suspending user code inside fill. Preserve custom marshaller compatibility; existing iOS assumption that Source is Buffer is itself a constraint to address.

**Impact:** large uploads and request allocation pressure across unary/streaming; genuinely closes a baseline difference even though legacy shares it. **Confidence:** high extra intermediate representation, medium net benefit. **Owner/effort/risk:** generated protobuf + marshaller API + bridge, large; size mismatch, mutation between sizing/encode, failure cleanup. **Experiment:** isolated encode/copy phase counters at 1k/1m/near4m and end-to-end uploads; vary message fields, not only a single bytes body. Do not double encode to obtain size.

### O11. Decode directly from scoped Swift bytes (G)

**Current/location:** `decodeMessage` calls `copySwiftBytes` before `WireDecoderNative`, despite being inside `withUnsafeBytes`. SwiftProtobuf consumes that encoded input directly. (K4–K5,P3–P4,D9)

**Design:** optional native decoder initializer from a borrowed contiguous pointer, length and scope; parse entirely before callback returns and copy only fields requiring owned Kotlin representation. The current WireDecoder factory requires Buffer/Source; simply wrapping a pointer as today's Source will not remove its buffering assumption. Keep fallback for custom marshallers and avoid exposing borrowed views through public ByteString.

**Impact:** large responses, small-response allocation pressure, high concurrency; likely limited large-stream wall gain when transport dominates. **Confidence:** high copy exists, medium net speedup. **Owner/effort/risk:** protobuf/marshaller + bridge, large; no pointer escape, bounds/recursion/unknown fields, errors and GC pinning. **Experiment:** copy-byte count should fall by serialized response size per message, without changing payload ownership; compare response1k/1m and slow retained consumers. Decode-in-callback CPU must not block a NIO event loop (current callback originates in a Swift Task, but redesigned delivery must preserve that distinction).

### O12. Replace or specialize native protobuf field bridge (G)

**Current/location:** `WireEncoderNative`/`WireDecoderNative` call C wire operations per field and pin/callback for buffers. Generated code knows field schema. **Baseline:** SwiftProtobuf uses generated traversals with native Swift encoder/decoder operations. (P1–P5,D9)

**Design:** benchmark a Kotlin-native wire implementation or generated bulk encode/decode path for common primitive/bytes fields; preserve protobuf semantics for unknown fields, enum values, recursion, packed fields, UTF-8 and malformed input. A specialized bytes-message path can test mechanism but must not become benchmark-specific production behavior. Large C++ `WriteAliasedRaw` can already directly call the sink for large blocks, so do not assume a full extra C++ staging copy on all writes.

**Impact:** all current calls, especially small-message CPU/concurrency and large-upload medians. **Confidence:** medium structural value, low-to-medium performance outcome: pure Kotlin is not automatically faster than C++. **Owner/effort/risk:** protobuf/codegen, large, conformance risk. **Experiment:** matched schema encode/decode microbenchmarks, allocation/crossing counts, then four representative RPCs. Run protobuf conformance before adopting. This can improve legacy too; that does not exclude it.

### O13. Remove zero-fill before overwriting raw request storage (G/S)

**Current/location:** `copyToRawMessage` calls `RawMessage(repeating:0,count:)`, then fills every byte; public transport bytes expose only initialized readable storage. **Baseline:** SwiftProtobuf's `serializedBytes` also initializes zeroed storage then writes encoding. (B4,D8–D9)

**Design:** upstream initialization API that reserves ByteBuffer capacity, fills writable bytes, validates exact bytes written, then advances writerIndex; no temporary array and no representation cast into an internal field. A bridge-only use improves C against the fixed S baseline; using it in SwiftProtobuf improves both and reduces relative benefit.

**Impact:** large request memory traffic; smaller than O10 if combined, benefits overlap. **Confidence:** high explicit zeroing, low-to-medium measured effect because optimization/memory bandwidth unprofiled. **Owner/effort/risk:** NIO transport/core bytes API, small–medium upstream, uninitialized memory safety. **Experiment:** zeroed-byte and memory-bandwidth counters; same initializer in both clients as a separate control. Reject unsafe uninitialized readable bytes or fill failure returning success.

### O14. Reduce metadata/status and descriptor work when unobserved (G)

**Current/location:** headers copy/credential merge, metadata visitor conversions, status linear enum lookup, full method string split and new descriptors each call; callback futures even with no subscribers. **Baseline:** generated method descriptor plus native Swift Metadata/Status; no Kotlin visitor. (K1,K7–K8,B3)

**Design:** cache immutable method descriptor components per method with bounded lifetime; optimize empty credentials/header copy into a transport-owned empty snapshot; lazily materialize metadata only when callbacks/error consumers need it; cache empty immutable internal metadata/status where safe, not publicly mutable instances. Keep status/trailers available for errors and duplicate/binary header ordering. Do not suppress observable headers callbacks or share mutable call options across calls.

**Impact:** small unary/concurrency, metadata-heavy calls not represented in CSV; low expected bulk effect. **Confidence:** high work exists, low share. **Owner/effort/risk:** common/Kotlin/Swift bridge, small–medium, mutation/interceptor semantics. **Experiment:** empty vs metadata-heavy A/B, exact callback ordering/contents, allocations per unary. Enum lookup alone waits for a profile; optimize larger objects first.

### O15. Reduce common Flow/event/future allocations (G)

**Current/location:** `rpcImpl`, `ClientCallScopeImpl.doCall`, `GrpcClientCallEvents`, two CallbackFutures and Message wrapper. Swift has its own async abstractions but no these Kotlin layers. (K1–K2)

**Design:** internal event sink with separate metadata/status callbacks and direct response collector; or specialized unary operation preserving the existing public API and generic interceptor fallback. Fuse internal forwarding layers where compiler does not already inline them. Keep a new call scope on each cold-flow collection/retry and cancellation precedence; shared transport abstraction remains protocol-internal and must work on non-iOS too.

**Impact:** allocation/CPU on small responses/unary, not automatically scheduler improvement. **Confidence:** high wrappers exist, medium-low marginal effect after O3–O5. **Owner/effort/risk:** kotlinx-rpc common, medium–large, cross-platform compatibility. **Experiment:** allocation stacks and empty/server1k CPU before/after isolated internal API variant; nonIos cancellation/interceptor tests. Removing all Flow APIs or forcing hot/shared streams is rejected.

### O16. Reduce ARC/boxing/callback traffic through bridge API shape (G,D)

**Current/location:** NSObject request/events/status/metadata, existential request source, completion closures, Kotlin interop wrappers and cancellation adapters. Direct Swift uses typed values and specialized generics. (B1–B4,K3–K8,D1)

**Design:** prefer scalar terminal fields or a combined owned result over nested wrappers; avoid repeated `length` getter crossings by snapshotting validated length; use bounded request/response batches to amortize closures. Keep payload owner alive to final synchronous consumption. Consider a C-compatible opaque handle plus callback ABI only if Objective-C entry/ARC shows material cost; this still needs explicit retain/release and cancellation ownership and does not remove runtime scheduling automatically.

**Impact:** small-message/high-concurrency CPU; exact ARC count unknown. **Confidence:** medium work, low marginal impact of scalar tweaks. **Owner/effort/risk:** bridge, small for length snapshot, large for ABI redesign; use-after-free/reentrancy. **Experiment:** interop entry counts, retain/release allocation sampling, generated bridge disassembly at Release. Do not weaken `@unchecked Sendable` invariants or reuse wrappers still visible to consumers.

### O17. Pool only proven hot buffers/resources with bounded ownership (G/S,D)

**Current/location:** Kotlin Buffer segments, native encoder allocations/cleaners, RawMessage buffers, NIO framer clears small buffers and drops large ones. Swift already benefits from ByteBuffer COW/reuse. (K5,P2–P4,D6–D8)

**Design:** measure allocator stacks first; reuse an encoder only after explicit safe reset/release semantics (O1); use per-call/per-executor bounded pools with size classes and maximum retained bytes, not a global contended cache. Investigate existing kotlinx-io segment reuse before adding duplicate pooling. COW ownership can force copies when buffers are retained by async sends.

**Impact:** large uploads/concurrency, possibly tail pressure. **Confidence:** medium allocation sources, low net benefit; pooling can worsen memory/contended locks. **Owner/effort/risk:** protobuf/bridge/NIO, medium–large, stale data and aliasing. **Experiment:** allocations, retained capacity, COW-copy counters under slow readers/cancel; inspect reset correctness. Reject unbounded pools, pooled public messages, or GC disabling. Compare both clients for shared NIO pool changes.

### O18. Tune Kotlin scheduling, GC and reclamation from profiles (G,D)

**Current/location:** request source's SupervisorJob and undispatched collector/pull jobs, Kotlin Default benchmark workers, per-message protobuf/interop allocations. **Baseline:** no Kotlin GC/dispatcher. (K3,H1,P2)

**Design:** first remove lifetime/allocation defects and isolate current binary optimization. Then A/B dispatcher parallelism and supported runtime GC settings with exact compiler build recorded; distinguish queue delay, GC stop time and native cleaner work. Preserve flow context: executing arbitrary Flow collection directly on a Swift/NIO thread may violate Kotlin Flow context and block event loops. A dedicated serial worker may reduce contention but also cap throughput.

**Impact:** potentially high for long-tail means, impossible to quantify now. **Confidence:** hypothesis, not demonstrated GC attribution. **Owner/effort/risk:** Kotlin integration/runtime configuration, small experiments, large tuning risk. **Experiment:** signposted call pauses aligned with GC logs/heap/live encoders, scheduler/CPU tracks and c1/c128. If stalls occur without GC or runtime backlog, reject that cause and inspect server and executor queues. Do not treat a larger heap as a fix for O1.

### O19. Disable or tune flush coalescing for latency-sensitive calls (S; possibly G against fixed baseline)

**Current/location:** both clients inherit `connection.flushCoalescing` defaults: 100 µs, 64 KiB. **Baseline:** same defaults. (B3,H2,D5)

**Design:** expose a connection configuration choice; first A/B `transportConfiguration.connection.flushCoalescing = nil` in each client, then smaller delay/threshold if needed. Connection-wide changes affect concurrent streams and throughput; do not imply a per-call flag exists.

**Impact:** small unary/ping-pong absolute latency, potentially substantial; unlikely to fix current-only tails or small-server-message consumer cost. Against an unchanged S it may exceed parity, but that is a configuration advantage, not removal of inherent Kotlin overhead. **Confidence:** high config, strong latency hypothesis. **Owner/effort/risk:** kotlinx-rpc configuration, small, syscall/energy/bulk-throughput tradeoff. **Experiment:** 2×2 current/Swift × default/nil, empty/1k/64k upload and mixed unary+bulk; record flush request/timer/fire, packets, CPU and p99.

### O20. Reduce NIO write submissions and transport framing copies (S/B)

**Current/location:** `NIOAsyncChannelHandler` has scalar and sequence writes; sequence loops share a flush. `GRPCMessageFramer.encode` copies payload into framing storage. **Baseline:** same machinery, different producer cadence. (D4,D6)

**Design:** use supported writer `write(contentsOf:)` where a bounded message batch already exists. The pinned `MapRPCWriter.write(contentsOf:)` transforms and forwards a sequence, and transport `Connection.Stream.Outbound` forwards it to the NIO writer; measure actual delegate submissions rather than assuming scalar calls are batched. For large identity messages, upstream framer could queue a five-byte header and retained payload buffers rather than concatenate; preserve compression path and aggregate promises. A call-site loop over `write` is not automatically one event-loop submission.

**Impact:** bulk throughput/CPU and task submissions; fairness and small-message latency may worsen. **Confidence:** high copy/submission path, medium-low effect. **Owner/effort/risk:** grpc-swift/NIO upstream plus bridge batching, medium–large, framing/promise/order/retention complexity. **Experiment:** event-loop submissions/flushes/copied bytes per batch, large uploads in both clients. Benefit to S can move the parity target; report fixed-baseline and matched-baseline results separately.

### O21. Reduce receive consolidation and Network.framework adaptation (S)

**Current/location:** deframer accumulates fragments; NIOTS Data→ByteBuffer copy; C then adds its own Buffer copy. **Baseline:** shares transport copies but not Kotlin intermediate. (D6–D7,K5)

**Design:** first O11 for owned scope. Upstream reduce unnecessary compaction/COW retention and explore Data-backed ownership; truly segmented decoding needs changes to contiguous-byte core/deserializer contracts, not just replacing an array in the bridge. POSIX versus TransportServices is an experiment on both clients, conditional on supported Apple deployment/connectivity/TLS requirements.

**Impact:** large-response bulk plateau, shared CPU improvement; not a proven bridge gap. **Confidence:** high mechanisms, low bottleneck attribution. **Owner/effort/risk:** NIO/transport/GRPCCore, large; fragmentation, compressed/truncated messages, buffer ownership, platform behavior. **Experiment:** copy volume and allocation stacks across 16k/64k/1m frames; complete-vs-fragmented fast-path counters, both clients and slow consumers. Do not claim zero-copy receive from simply retaining ByteBuffer slices.

### O22. Tune HTTP/2 windows, frame size and read watermarks only on observed stalls (S)

**Current/location:** 16 KiB max inbound frame, 8 MiB target receive window; NIO inbound watermarks 2/10 elements; window replenishment accounts for buffered frames. **Baseline:** same defaults. (D3–D5,D10)

**Design:** expose supported HTTP/2 config and instrument flow-control stalls before changing it. Receiving larger frames requires peer compliance; larger client receive window primarily affects downloads, while uploads need server receive settings. Read watermark changes likely require transport initializer/config work; test byte-sensitive budgets because ten MiB messages differ greatly from ten 1k messages.

**Impact:** bulk high-BDP/fragmentation cases; loopback already has large window, no established benefit. **Confidence:** high defaults, low optimization priority. **Owner/effort/risk:** configuration/NIO, small experiment to medium upstream, memory/fairness. **Experiment:** frame histogram, SETTINGS, WINDOW_UPDATE, blocked-window duration, bounded RSS and mixed traffic. If blocked duration is negligible, reject larger windows as explanation. Never disable flow control or inflate limits merely for the benchmark.

### O23. Executor affinity and transport stream scheduling (G/S,D)

**Current/location:** bridge Tasks plus NIO off-loop `execute` submissions; shared channel/subchannel mutexes and async stream opening. **Baseline:** fewer outer hops but same stream scheduling. (B1,D1–D4)

**Design:** remove O3/O6 handoffs before inventing a scheduler. Investigate supported executor preference/affinity only with recorded Swift runtime/compiler and NIO invariants; actor serialization may increase queueing. Co-locate small bridge state transitions if safe, but keep user Kotlin callbacks and serialization off event-loop critical sections. One long-lived call owner is preferable to a Task per event, not necessarily a dedicated OS thread.

**Impact:** small-call/high-concurrency CPU, possible contention relief; not a guaranteed latency cut. **Confidence:** hypothesis; static code cannot establish real executor hops. **Owner/effort/risk:** Swift bridge or upstream, large, starvation and thread safety. **Experiment:** runnable-to-running delay, thread/executor IDs and event-loop queue depth at c128/server1k. If code is CPU-bound rather than queued, affinity is unlikely to help. Do not invoke unsafe NIO sync operations off-loop.

### O24. Verify optimizer visibility and build symmetry (G)

**Current/location:** imported Swift package, generic/existential request API and native Kotlin Release executable; HEAD's `configureSwiftPMXcodeBuildConfiguration("Release")` targets fingerprint/dump Xcode tasks. **Baseline:** explicit SwiftPM release, typed generated generic client. (G2,B5,H5)

**Design:** capture effective xcodebuild/swiftc/konanc commands and binary hashes, not just task names. Confirm workaround reaches import/link build; compare clean Release artifacts. Only then test specialization/inlining or whole-module optimization changes with measured code-size/CPU tradeoffs. **Impact:** potentially broad if CSV used unoptimized Swift; otherwise mostly measurement prerequisite and narrower generic dispatch costs. **Confidence:** high history, unknown CSV flags. **Owner/effort/risk:** build configuration/bridge, small audit, medium optimization work; no blind fast-math/unchecked optimization. **Experiment:** same pinned toolchain and dependencies, current before/after effective Release, both direct and bridged minimal calls; inspect hot thunk/generic symbols. No additional production “set Release” fix is proposed: HEAD already contains it.

### O25. Separate harness setup cost and stabilize experiments (B)

**Current/location:** streaming builds request/ByteString inside measured outer scope; Swift constructs Data; sample arrays/task workers and teardown differ. Fixed current→legacy→Swift order and independent simulator selection. (H1–H9)

**Design:** retain original end-to-end benchmark as the primary compatibility result, add prepared-payload and streaming-only timing variants with equal semantics to both clients; export exact simulator ID, randomize client/case order and preserve raw timestamps. **Impact:** more trustworthy large/fixed-byte ceiling estimates; may change numbers without improving backend. **Confidence:** high measurement issue. **Owner/effort/risk:** benchmarks, small–medium, interpretation rather than production risk. **Experiment:** near4m prepared vs original in both clients, long repeated streams, process-per-case versus all-in-one process; capture RSS/encoder live counts. Throughput gains from moving preparation are labeled harness changes only.

### O26. Connection sharding, compression and workload changes (B/S,D)

**Current/location:** both reuse one warm channel per case. Core uses per-connection HTTP/2 multiplexing and default no request compression. **Baseline:** same basic design. (B3,H2,D3,D5)

**Design:** connection pools/sharding only if profiling proves one event loop/HTTP2 connection is saturated; compare S with the same pool. Compression only for a separate realistic workload with CPU/wire-byte accounting; modulo-251 payloads are highly compressible. Larger messages/batching at application level change latency and message semantics. Keep them separate from bridge optimization.

**Impact:** may improve absolute throughput or remote-link performance; no evidence they remove the current single-channel gap. **Confidence:** low for supplied loopback cases. **Owner/effort/risk:** configuration/application/upstream, medium, ordering/load-balancing/resources/energy. **Experiment:** 1/2/4 channels in both clients, compression off/on with incompressible controls, peer CPU and wire bytes. Do not recreate channels per call; reuse is already implemented.

### Rejected or deferred shortcuts

- **Rejected:** remove checked continuations/cancellation checks for speed. Exact-once callback completion, cancellation wakeups and terminal delivery are correctness obligations; unchecked continuation substitutions need measured benefit and do not remove scheduling.
- **Rejected:** collapse both duplex directions into a single serial send-then-receive loop. Full-duplex wins demonstrate the value of overlapping directions; serializing can deadlock asymmetric producer/consumer flows. Combine lifecycle ownership, not dependent progress.
- **Rejected:** retain pointers from `withUnsafeBytes`/Kotlin pin scopes into async writers; consume or copy synchronously unless an explicit owned-storage contract is introduced.
- **Rejected:** cache serialized mutable messages or skip response decode/validation in current only. Prepared-byte calls are diagnostic/B variants; production caching requires immutability/version invalidation and bounded storage.
- **Rejected:** describe `RawMessageSerializer` as a second protobuf encode or `RawMessageDeserializer` as a second protobuf decode. They cast the already-serialized transport bytes; optimize their representation only if a profile shows cost. Their forced cast constrains transport bytes type and must be revisited if transport representation changes.
- **Rejected:** share mutable ByteBuffer/message/status objects across live requests or pool before ownership is fixed; uncontrolled parallel request pulls or event pulls violate documented contracts.
- **Deferred:** micro-optimize status enum scan, unchecked type casts or iterator wrappers before task/resource/byte-path measurements. They are not plausible explanations for 0.4s pauses without further evidence.
- **Deferred:** a direct Swift-native generated client API exposed to Kotlin could move protobuf work into Swift, but still must materialize Kotlin values and would be a large codegen/API strategy with its own baseline; it is not a drop-in bridge tweak.
- **Deferred:** packed repeated-field loop/vector optimizations are credible for other schemas (native encoder explicitly loops through packed values), but these bytes-dominated benchmarks cannot establish their contribution. Add schema coverage rather than extrapolating these results.
- **Rejected:** compare current with tuned settings to unchanged Swift and call all improvement “bridge parity.” Always retain fixed-S and matched-S comparisons.

## 7. Attainable-performance analysis

### Model and limits

For sequential latency define excess over Swift as Δ=C−S. If fraction q of that excess is removed while S stays fixed, retention becomes:

`R_after = S / [S + (1−q)(C−S)] = 1 / [1 + (1−q)(1/R_before − 1)]`.

For throughput, the same expression can be used only as a *service-demand sensitivity model*, not a wall-time decomposition of parallel pipelines. It assumes the shared bottleneck, concurrency, workload and Swift baseline remain unchanged; removing a bottleneck can invalidate it. It cannot be applied meaningfully to negative excess in winning current cases. Proposed improvements overlap; do not multiply O1–O26 speedups.

| Representative measured retention | Remove 25% of modeled excess | Remove 50% | Remove 75% | Remove 90% |
|---|---:|---:|---:|---:|
| Small unary 87% | 89.9% | 93.0% | 96.4% | 98.5% |
| Small response stream 62% | 68.5% | 76.5% | 86.7% | 94.2% |
| High-concurrency unary 36% | 42.9% | 52.9% | 69.2% | 84.9% |
| Large upload unary 19% | 23.8% | 31.9% | 48.4% | 70.1% |
| Large response stream 93% | 94.7% | 96.4% | 98.2% | 99.3% |

These are **calculated sensitivity scenarios**, not predicted results. In particular, reaching 90% from 19% requires removing about 97.4% of the modeled excess; reaching 90% from 36% requires removing 93.8%. A claim that one small bridge tweak will get either workload to 90% is not rational. At 62%, reaching 90% requires removing about 81.9% of modeled excess; O3 plus serialization/allocation changes would need to address most of it.

Conservative scenarios allow incomplete structural gains; optimistic ones require successful lifetime/byte-path work and no replacement bottleneck. Shared transport tuning must be evaluated again against equally tuned Swift. Percentages refer to throughput/mean-latency retention; tails need independent validation.

### Residual floor: what is inherent, what is not

**Observed residual work:** a Kotlin public API needs Kotlin request/response objects, coroutine/Flow semantics, cancellation/metadata integration, and some transition into the Swift transport. Owned ByteString response fields require lifetime-safe Kotlin storage under the current API. Swift also owns a decoded Data field, so one owned-field copy is not uniquely Kotlin overhead. Extra encoded Buffer copies, task-per-event, per-pull coroutine creation and cleaner cycles are **not** inherent to crossing a language boundary. (K1–K8,P1–P4,D9)

**Strong inference:** bridge/representation work can be hidden behind server/network/framing time in bulk pipelines; existing wins demonstrate that equal throughput does not require equal instruction count. Under real network latency small-call percentage parity may improve as the common network component increases, but energy/CPU overhead remains. This simulator-loopback dataset cannot quantify device or WAN behavior.

**Unknown:** a lower bound in microseconds or percent for the best correct Kotlin/Swift boundary. We have no isolated optimized boundary measurement, CPU profiles, memory-bandwidth limit or compiler-generated thunk inspection. There is no defensible unavoidable “at least 10%” penalty. A useful planning residual for the near-parity target workloads is about 2–10% in throughput/mean latency under the stated assumptions; it is not a proved architectural tax. For high concurrency and uploads, no universal residual range is justified.

**Direct answer:** near parity is plausible for sequential small calls, ping-pong, response-heavy bulk, and pipelined duplex; small-message response streams have a credible path to much closer parity but need most handoff overhead removed. High-concurrency unary and large uploads should currently be described as “substantial gap reduction possible, ceiling unresolved.” Exact throughput parity is architecturally plausible and already observed in some shapes. Exact parity across CPU, allocations, energy and every tail percentile is neither expected nor evidenced. The measurement most likely to change this assessment is a provenance-controlled Apple run that aligns per-call stalls with live encoder/StableRef counts, GC/cleaner activity, and Swift/Kotlin scheduler delays, followed by isolated O3 and O10 A/B variants.

## 9. Validation plan

### Minimum Apple experiment matrix

Build one baseline and one isolated variant at a time, retain binaries/dSYMs/commands and lockfiles, and run client orders in alternating/randomized blocks. Begin with at least five independent repeats per short case as an initial variance check, then extend only where variance or a tail hypothesis requires more data. Keep per-run results, paired effect sizes and raw timestamps; a sample count is not itself proof of statistical power. Use identical payload, warmup, peer binary and simulator ID. Add physical-device validation after simulator effects are understood.

Useful instrument suite: Instruments Time Profiler for on-CPU stacks; Swift Concurrency for task creation and runnable delays; Allocations/retain-release sampling for Swift/Objective-C; Kotlin/Native GC logs/statistics and heap/live-object counters for Kotlin; signposts for bridge/serialization/terminal boundaries; scheduler/thread tracks for off-CPU time; peer CPU/server trace and network frames for common bottlenecks. Counts should be per RPC, request message, response message and application/wire byte. CPU profiles alone do not explain waiting time; total RSS alone does not distinguish retained encoders, allocator caches and active network buffers.

### Correctness gates for structural experiments

Exercise empty request streams; multi-element unary violations; request Flow initialization before failure; headers-only rejection; status after one/many messages; cancellation before registration/during encode/during send/during response pull; concurrent invalid pulls; callback reentrancy; exception thrown by each interceptor callback; deadlines; normal EOF; peer disconnect; slow reader/writer; duplicate and binary metadata; compressed and truncated messages; retained response payloads after RPC completion. Validate exactly-once completion, fresh scope on recollect/retry, bounded bytes, no pointer escape, and no native double release. Do not cancel the producer while holding a lock it may reenter.

For shutdown, record both user-visible completion and all-call-resource release. A variant that returns earlier but leaves accumulated tasks/native resources is not a successful optimization. For no-copy experiments, run sanitizer/lifetime tests and protobuf conformance before timing comparisons. These are future Apple/native experiments, not checks claimed executed during this run.

## 10. Open questions and residual uncertainty

1. Which binaries, compiler/runtime versions and effective optimization flags produced this CSV? Did it precede the new imported-Swift Release setting?
2. Does the native encoder stable-reference graph retain encoder/sink resources in those binaries, and does live growth correlate with the long tails? What is the actual native decoder destruction sequence under sanitizers?
3. Are 0.2–0.4s pauses GC/cleaner activity, executor starvation, native allocation, server interference, or a combination? Raw sample timestamps are required.
4. How much CPU/allocation is attributable to response Task/channel handoffs versus Kotlin protobuf parsing and the encoded-input copy? Does O3 alone recover most of the ~5.5 µs/message effective budget?
5. How much large-upload time is request creation, native wire encoding, Buffer filling, Swift copy/zeroing, scheduler waiting or completion? What remains after both harness preparation and outliers are measured separately?
6. What effective batching/frame fragmentation, COW-copy volume and window-blocked duration occurs on the Apple transport? Defaults alone do not determine these.
7. Can optional single-request/single-response and pointer-backed native marshallers preserve all existing custom-marshaller/interceptor semantics without making the public API platform-specific?
8. Are the full-duplex wins stable across randomized repeats and matched-build clients, and what phase/batch pattern explains them?
9. Do simulator gains hold for device CPU, memory, energy, TLS and realistic network latency? No extrapolation from loopback establishes this.
